# Trend Hunter 中文导读与面试手册

这份文档的目标不是让你背代码，而是让你能用自己的话回答三件事：项目要解决什么、为什么这样设计、目前哪里还不够好。

## 1. 先把问题说成人话

输入是 90 天、约 4.8 万条中文游戏社区消息，来自 QQ、Bilibili、微博、Steam、TapTap、Discord 和 Bahamut。题目不会预先给类别，也没有点赞或评分。

程序需要在任意一个 `--as-of` 日期回答：

> 截至当天，玩家刚刚开始集中谈论哪些“故事”？它是新出现、持续增长、一次性事件、正在消退，还是人为刷出来的？

“故事”不是单个关键词。例如“抽卡纪录”“出金率低”“公示概率”“暗改爆率”可能都属于同一个玩家信任危机。

## 2. 输入和输出契约

评测方会运行：

```bash
python run.py --input voices.jsonl --as-of 2026-07-24 --out trends.json
```

最重要的限制是：程序只能读取 `--as-of` 当天及以前的消息。否则就发生时间泄漏，相当于用未来答案作弊。

输出最多八个趋势，每个趋势包含：

```json
{
  "title": "玩家怀疑抽卡概率被暗改",
  "title_en": "Players suspect a silent gacha-rate nerf",
  "category": "Gacha economy & trust",
  "status": "new",
  "first_seen": "2026-07-18",
  "voice_ids": ["..."],
  "why": "最近 7 天出现 38 条，覆盖 Bahamut 与 Discord……"
}
```

`voice_ids` 很关键：评审会直接回看这些原始消息，判断结论是否真的有证据。

## 5. 算法逐步解释

### 5.1 加载数据并锁死时间边界

`load_voices()` 把时间统一到香港时区，只保留 `day <= as_of` 的消息。过滤发生在任何统计或模型拟合之前，所以未来信息不可能影响词表、频率或排名。

随后进行 Unicode 归一化、繁体转简体、移除 URL/图片/mention 等平台噪声，同时保留 `doge` 这种会改变语气的信号。

### 5.2 恢复短回复的语义

“确实”“+1”“笑死”单独看没有意义。`_add_reply_context()` 会把普通玩家父消息附到这些短回复后面。

但如果父消息是官方 PV、公告或攻略，短回复不会被扩成独立趋势证据。这样可以减少官方内容带来的假热度。

### 5.3 用字符 n-gram 找新语言

`CountVectorizer(analyzer="char", ngram_range=(2, 9))` 将文本拆成连续 2–9 个字符的片段。

选择字符而不是中文分词有三个原因：

1. 新外号、拼写错误和中英混写不在现成词典里；
2. 简繁体归一化后，相同玩家语言更容易落在一起；
3. 题目要求发现“还没有名字”的趋势，预设主题词典反而会限制发现。

### 5.4 比较不同时间窗口

对每个短语统计：

- `c3`：最近 3 天；
- `c7`：最近 7 天；
- `p7`：再前一个 7 天；
- `p14`：更早的 14 天；
- `old14`：42 天窗口中最早的 14 天。

系统分别计算四种变化：近期增长、近期下降、新颖度和三日加速度。这里用 `log1p` 压缩大数字，避免一个超大话题完全淹没小而重要的新故事。

系统轮流从四类变化中取候选，而不是只排一个总榜。这样一场大规模刷屏不会用相似口号占满所有候选位置。

### 5.5 把短语合成故事

如果两个短语经常出现在同一批消息里，`_cluster_seeds()` 会把它们放入一个候选故事。之后再用字符 TF-IDF 和余弦相似度去掉语义高度重叠的候选。

这里是两层去重：

1. 消息集合重合度高，说明它们可能是同一故事；
2. 证据文本的字符 TF-IDF 相似，说明不同措辞可能表达同一件事。

### 5.6 判断趋势状态

`_topic_status()` 使用消息量、活跃天数、平台分布、用户数、峰值集中度和重复模板比例：

- `new`：近一周首次形成可信规模；
- `growing`：比前一周明显增加并持续多日；
- `one-off`：单日峰值很高，随后快速消失；
- `fading`：前一周有量、最近明显下降；
- `not real`：高度集中在一个平台、账号很多但措辞模板高度重复。

`first_seen` 不是某个通用词第一次偶然出现，而是本轮事件开始形成规模的日期。

### 5.7 选择可审计证据

`_representatives()` 优先选择不同平台、不同作者、最能覆盖候选短语的消息。这样 `voice_ids` 不只是六条重复文案，而是能显示故事如何传播的证据组合。

### 5.8 LLM 只负责语义，不负责发现热度

如果有 `OPENAI_API_KEY`，本地算法先产生最多 18 个候选，再用一次 Structured Outputs 调用：

- 合并同义故事；
- 理解中文俚语、反讽和昵称；
- 写自然的中英文标题；
- 给出工作室能采取行动的解释。

LLM 看不到 `as-of` 之后的数据，也不能自行创造 `voice_ids`；最终证据 ID 仍由本地代码从候选消息中选择。

没有 key、网络失败或模型不可用时，程序自动使用本地规则输出有效 JSON。这保证评测不会因为外部服务失败而崩溃，但本地标题的语义质量明显弱于 LLM 路径。

## 6. 2026-07-24 的实际例子

程序在这个日期成功找到两个最重要的新故事：

1. 赛琳娜在 PvP 中过强：7 月 21 日出现，四天内传播到七个平台；
2. 玩家开始导出抽卡记录并怀疑公示概率：7 月 18 日出现，先在 Bahamut 和 Discord 形成证据。

它也正确识别了匹配机制讨论正在回落。

但是纯本地标题存在明显问题，例如把“Selena is broken”截成 `aisbroken`，或者把同时包含 PvP 字样的混杂候选都命名为 PvP 争议。这正是当前最需要用真实 API 回归测试的部分。

## 7. 当前优点与不足

### 优点

- 时间边界在加载阶段强制执行，防止 hindsight；
- 不依赖预设游戏词典，能发现新外号和新抱怨；
- 同时区分增长、下降、事件峰值和协同刷屏；
- 有跨平台、跨作者的可审计原始证据；
- LLM 只做小规模语义整理，成本和随机性受控；
- 无 API 时仍可运行，且有自动测试。

### 不足

- 目前只有 3 个自动测试，覆盖面不够；
- 状态阈值是启发式规则，不是从标注集学习得到；
- 本地 fallback 的标题规则容易被候选中的某个无关词触发；
- `core.py` 超过一千行，后续可以拆成预处理、发现、评分和渲染模块；
- 还没有用主办方 key 完成 LLM 路径的端到端回归；
- 尚未建立一套人工标注的多日期评估表来计算 precision/recall 或 early-detection lead time。

面试时不要隐藏这些不足。能准确指出失败案例和下一步，比声称模型完美更可信。

## 8. 两分钟项目介绍

你可以先理解逻辑，再改成自己的表达：

> 我把这个任务看成无监督的时间变化检测，而不是普通文本分类，因为类别事先不存在。程序先在香港时区严格截断 as-of 之后的数据，再做简繁体和平台噪声归一化，并给“确实”“+1”这样的短回复补充父消息语境。候选发现用字符 n-gram，因为它对中文新外号、错别字和中英混写更稳健。每个短语会比较最近 3 天、7 天和此前几个窗口的增长、衰退、新颖度和加速度，然后按消息共现聚成玩家故事。状态判断还看跨平台传播、活跃天数、峰值集中度和重复模板，因此能区分持续趋势、一次性事故与协同刷屏。最后 LLM 只对本地候选做一次语义合并和命名，证据 ID 与时间边界仍由确定性代码控制。这个设计的核心是：统计负责判断什么时候发生变化，语言模型负责解释玩家到底在说什么。

## 9. 高频面试问题

### 为什么不用 LDA/NMF 主题模型？

它们更容易找出整个语料长期存在的大主题，如抽卡、性能、美术，却会埋掉昨天刚出现的小故事。这个题目更关注时间变化，而不是全局主题结构。

### 为什么不用 embedding 直接聚类？

可以作为下一版，但全量 embedding 成本更高，而且仍需要单独设计时间评分。字符 n-gram 对新造词更透明，评审可以直接追踪哪个短语在何时增长。当前 TF-IDF 只用于候选去重，不负责最终解释。

### 怎么证明没有偷看未来？

`load_voices()` 在任何拟合前按香港日期过滤；测试包含一条未来消息并断言它不会进入数据。可以在多个 `as-of` 日期重复运行，查看趋势何时首次出现。

### 如何识别刷屏？

看四个联合信号：单平台占比、独立用户比例、近重复模板比例、活动是否突然停止。只有量大不能证明真实热度。

### LLM 会不会幻觉？

LLM 只能从已经发现的候选 ID 中选择和合并，输出由 Pydantic schema 限制；`voice_ids` 由本地代码产生。如果调用失败则自动回退，不影响输出格式。

### 如果再多一天，你会改什么？

先建立 6–10 个 `as-of` 日期的人工答案表，量化 top-8 precision、首次发现提前量和状态准确率；再针对误报调整候选纯度，并增加 time leakage、one-off、not-real、LLM merge 的测试。

## 10. 建议学习顺序

1. 亲手运行 `run.py`，打开生成的 JSON；
2. 在 `run.py` 给四个主函数设置断点或临时打印长度；
3. 阅读 `load_voices()`，确认未来消息在哪里被过滤；
4. 阅读 `_seed_candidates()`，用自己的话解释四个时间窗口；
5. 阅读 `_topic_status()`，手算一个 `new` 和一个 `fading` 案例；
6. 阅读 `refine_with_openai()`，解释 LLM 被允许和不被允许做什么；
7. 运行 `pytest -q`，逐个解释三个测试防止了什么错误；
8. 不看文档，自己完成一次两分钟项目介绍。

真正的验收标准是：你能打开任意一个趋势，沿着 `voice_ids` 回到原始消息，解释为什么它在当时属于这个状态，并指出算法可能错在哪里。
